# API v1 — development contract

Base: `/api/v1/`. JSON, read-only GET endpoints. This is an early contract; stabilize and test before native clients. Times are integer service-day seconds in America/New_York. Values above 86400 refer to the following calendar day. A dated trip identity is `YYYY-MM-DD|feed:trip_id`. Entity IDs are namespaced by feed.

| Endpoint | Parameters | Result |
|---|---|---|
| `meta` | optional `compact=1`, `page`, `page_size` (1–1000) | API version, feeds/provenance, cities, routes, stops, limitations. `compact=1` omits large route/stop arrays; pagination is opt-in and returns `*_pagination` totals. |
| `live` | `provider=mbta`, optional `route`, `stop`, `alerts=0|1` | Opt-in provider overlay with `status=live|unknown`, predictions, alerts and limitations; never used by routing |
| `coverage` | `date=YYYY-MM-DD` | Per-feed imported status and service-range bounds |
| `departures` | `stop`, `date`, optional `route` | Boardable departures on that calendar day; coverage |
| `stops` | `q`, optional `feed`, `limit` (default 50, range 1–500) | Stop name lookup: case-insensitive substring matches over loaded stops only, returning id, name, feed and coordinates, plus total `match_count` and a `truncated` flag; prefix matches sort first; an empty query or a query with no matches returns an empty list — stops are never invented |
| `pdf-schedules` | optional `document` | Reviewed official PDF documents and normalized timetable rows, with hash, source URL, extraction/review status and routing eligibility. PDF rows are not routed yet. |
| `fares` | `from`, `to`, optional `route` | Source-backed fare lookup. Currently supports adult one-way CTrail Hartford Line station fares and the regular adult CTtransit local 2-hour fare; unsupported express, discount, pass and mixed-agency cases are explicit. |
| `route` | `id`, `date` | Active trips, published stops/shapes, dated weekday/Saturday/Sunday counts |
| `trip` | `id` | Ordered stop times (original service-day seconds) |
| `plan` | `from`, `to`, `date`, `time`, `deadline`, optional `routes` | Earliest itinerary or explicit no-result with coverage; `routes` is an ordered comma-separated route-ID chain |
| `reachability` | `from`, `date`, `time`, `deadline`, optional `page`, `page_size` (1–1000) | Reachable stop IDs, coordinates and earliest arrivals; pagination is opt-in and returns `stops_pagination` |
| `bubble` | `from`, `date`, `time`, optional `budget` (seconds, default 3600), `visit` (seconds, default 0), plus planning options and optional `page`, `page_size` (1–1000) | Percival Mobility Bubble: stops reachable within the budget **with a feasible return home by the end of the window**, each with arrival, latest return departure and legs; counts of evaluated-but-unreachable stops with reasons; `unknown` feeds/stops that cannot be evaluated from loaded data (missing data is not evidence of no service); per-source provenance and service periods; pagination is opt-in and returns `reachable_pagination` |
| `outings` | `from`, optional `to`, `date`, `time`, `home_by`, optional `stay` (default 7200), `outbound_budget` (default 3600), `radius`, `buffer`, `limit` (browse only, 1–100) | Scheduled outing verification. With `to`, returns an exact outbound and latest verified return, meeting window, home arrival, and `verified|ruled_out|unknown` reason. Without `to`, forward-certifies a bounded set of outbound-reachable candidate stops and explicitly reports unevaluated overflow as incomplete search. Walking is required for first/last mile in this version. |

Planning options: `mode=walk|scooter`, `radius=0..3000` meters, `buffer=0..3600` seconds, comma-separated feed IDs, namespaced route IDs, and `include_optional=1` to include optional networks such as LIRR when imported. Optional feeds are excluded by default. `time=0..86399`; `deadline` between `time` and 172799. `kind=depart|latest` searches the earliest or latest feasible origin start (latest at one-minute resolution). `return=0|1` and `visit=0..86400` add earliest and latest return feasibility within the same deadline. A route chain constrains transit legs in order while allowing repeated continuation on the current route; it does not guarantee a timed connection. Boolean options reject values other than `0` or `1`.

Errors use `{"error":"message"}` with HTTP 400 for invalid input, 404 for unknown endpoint, 500 for unexpected server errors. Boolean options accept only `0` or `1`; `kind` accepts only `depart` or `latest`; route-chain entries must be namespaced IDs. There is no authentication or write API yet; bind to loopback only. No CORS policy or trusted reverse-proxy handling is implemented.

`live` is intentionally not a timetable fallback. Verified adapters currently include the official MBTA V3 JSON API (`provider=mbta`) and CTtransit's official JSON realtime feeds (`provider=cttransit`); set `MBTA_API_KEY` when using a registered key. PVTA currently returns `unknown` because its public page confirms realtime service but does not publish a stable feed URL/schema. Provider failures are returned as `unknown`, not as HTTP 500s, and scheduled `/plan`, `/route`, `/bubble` and `/reachability` never call this endpoint.

`found: false` means no result under loaded data and calculation limits, **not** that no transit exists. `estimated: false` on a transit leg denotes published schedule data rather than an estimated ground link; it does not mean live service is verified. Current coverage checks indicate the feed's outer date range, not proof that every route operates on a date. Every route/leg includes a feed identifier resolvable to the source registry.

Outing status is deliberately three-state. `verified` means both returned itineraries were forward-checked against active scheduled data, including transfer buffers and estimated walking links. `ruled_out` means the active data was sufficient and records a specific reason such as no outbound inside the budget, no usable return, or too little meeting time. `unknown` means coverage or search completeness prevents a determination. Candidate browsing never assigns a status to stops beyond its reported evaluation limit. `/api/v1/reachability` is unchanged.

Known contract gaps: unified PDF confidence/validation statuses, per-trip provenance/expiry gates, and authenticated persistence. Pagination and the current endpoint-level parameter validation are implemented, but broader schema/fixture coverage is still required before an iOS client depends on v1.
