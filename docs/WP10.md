# Windows Phone 10 (EdgeHTML) build

The Atlas web app also ships a Windows Phone 10 variant at **`/wp10.html`**,
served by the standard launcher exactly like `index.html` (the server serves
the `web/` directory). It exists for the Windows 10 Mobile emulator/device
path in the project's platform chain (web → Linux package → Windows Phone 10).

## Why a separate build

EdgeHTML — the Windows 10 Mobile Edge engine — cannot *parse* the modern
`web/app.js`. An audit of the shipped app (2026-11-15) found 14
optional-chaining (`?.`) sites and 2 optional catch bindings, all fatal
syntax errors on EdgeHTML, plus runtime gaps (`Element.replaceChildren`,
`Object.fromEntries`). CSS `color-mix()` degrades cosmetically. The modern
app is unchanged; the WP10 variant is a build of it:

- `web/app-wp10.js` — `web/app.js` transpiled with esbuild
  (`--target=es2017 --format=iife`), with `web/polyfills-wp10.js` prepended
  (polyfills for `replaceChildren`, `Object.fromEntries`, `Element.remove`).
- `web/wp10.html` — `index.html` with the script tag pointed at
  `app-wp10.js`.
- `scripts/build_wp10.sh` — the regeneration recipe. **Re-run it whenever
  `web/app.js` changes**, then re-verify on the emulator; the committed
  bundle is the verified build of the app.js from the PR #71 integration
  (2026-11-15), not a live mirror of later app.js edits.

## Verification status

The committed bundle was verified in Chromium on 2026-11-15 (loads with zero
page errors; contains zero optional-chaining sites). The decisive test —
running it in the actual Microsoft Emulator for Windows 10 Mobile on a
Windows Pro host — is still outstanding and is the owner's step; nothing
here claims EdgeHTML rendering is proven until that run happens. Inside the
emulator, never use `localhost` (it is a separate Hyper-V machine): browse
to the host's LAN address.
